# Test scenario — Regulated insurance case management

## 1. Opening description

Start a new DBA Agent session using only the text below. Do not provide the expected outcome to the agent.

> An insurer is building a centralized claims investigation and audit system. Adjusters handle cases, supervisors approve settlements and auditors inspect prior versions of sensitive claim records. The organization wants database-managed history and access controls rather than relying solely on application logging.

## 2. Canonical interview answers

Answer the agent's dynamically generated questions using the facts below. Where a question combines categories, combine the relevant facts. Do not invent additional requirements.

- **Entities and attributes:** Policy (ID, unique policy number, customer reference, effective/expiry dates); Claim (ID, unique reference, policy ID, region ID, opened time, status, claimed amount decimal); Assignment (ID, claim ID, adjuster reference, assigned time, optional ended time); Evidence (ID, claim ID, external file reference, hash, created time); Assessment (ID, claim ID, assessor reference, amount, decision); Settlement (ID, claim ID, amount, approved by, approved time, unique payment reference); Region (ID, unique code); AuditEvent (ID, actor reference, action, entity reference, timestamp). Track changes to Claim and Assessment with system-managed temporal history.
- **Relationships:** Policies have many claims; claims have assignments, evidence, assessments and settlements; claims belong to regions; a claim may have multiple historical assignments but at most one active assignment.
- **Volume:** 2 million policies, 1 million claims, 10 million history/audit rows; 120,000 claims/year, 15% yearly growth; retain claims and history for 10 years; expected hundreds of GB.
- **Workload:** 300 concurrent employees, up to 50 simultaneous writers; reports include claim history as of a past time, regional summaries and settlement review. Online queries should usually respond within two seconds; no claimed benchmark.
- **Transactions:** Approval and settlement plus audit event atomic; prevent duplicate payment references, lost updates and total settlements exceeding authorized amount. History must be maintained automatically on updates/deletes of temporal tables.
- **Security:** Central directory identity, database-enforced row-level security by region, read-only auditors with approved cross-region access, separation of adjuster and settlement approver, encrypted connections/backups. Test data synthetic only, no real PII.
- **Business rules:** Effective date before expiry; nonnegative claim/assessment amounts, positive settlement; statuses open/in_review/approved/rejected/closed; evidence hashes required; active assignment unique per claim; approved settlement requires approver and timestamp; temporal periods system-generated.
- **Deployment:** Existing Microsoft enterprise platform with SQL Server 2022 licenses, DBA/operations support and reporting infrastructure. Security team requires supported system-versioned temporal tables and native row-level security policies integrated with the existing SQL Server deployment. No trigger-based replacement of temporal history accepted. RPO 15 minutes, RTO 1 hour.

## 3. Follow-up guidance

- If asked about temporal history: use native system-versioned tables, not a manually maintained history table; operational audits remain separate.
- If asked about identity: directory identity mapped to roles/region membership; no passwords in the schema.
- If asked about evidence: object storage only, retain immutable hash and file reference.
- If asked about seed: use synthetic identities; temporal period columns are generated by the database and should not be inserted as ordinary values.
- For a genuinely unlisted noncritical detail, say it is not required for this scenario. For a material unknown, say it is unspecified and let the agent ask for clarification; do not fabricate an answer or imply the expected DBMS.

## 4. Expected outcome — evaluator only

**Do not send this section to the agent.** The expected outcome is a reasoned test oracle, not the result of a benchmark or an executed agent run.

- **Expected `selected` value:** SQL Server
- **Strength of expectation:** Strong

### Selection rationale

Existing Microsoft/SQL Server estate plus explicit native system-versioned temporal tables and row-level security make SQL Server a direct fit. MariaDB also has temporal features and PostgreSQL has row-level security, but neither meets the specified same-platform deployment without changes. SQLite does not provide the requested native security/temporal architecture.

### Additional design and SQL checks

- Expect system-managed temporal history, row-level security design, valid status and amounts, unique payment reference, and active-assignment uniqueness.
- Test negative amount, duplicate payment reference, invalid dates, orphan evidence, and invalid explicit values for generated temporal columns.
- A plain successful seed run cannot prove temporal history or security policies: test updates, as-of queries, and distinct role/region access separately.

Check these only after the agent selects a DBMS. The exact table names and implementation may differ. Seed conflict examples are optional negative tests to inject into a disposable copy of the output, not requirements to generate invalid data. Some cross-row and concurrency rules require separate transactional tests.
