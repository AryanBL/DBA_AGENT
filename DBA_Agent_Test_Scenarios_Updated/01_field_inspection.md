# Test scenario 01 --- Offline field inspection toolkit

> **Use only Section 1 to start the agent.** Keep Sections 2--4 as the
> interviewer answer sheet. Do not give Section 5 to the agent.

## 1. Opening description

A small engineering consultancy needs a portable application for
recording equipment inspections, measured values, defects, photographs
referenced by file path, and corrective actions. Inspectors work without
internet access at remote sites. Each laptop maintains a separate
project database. At the end of an inspection, a finalized copy is
handed to the office for read-only review. The application must work
without installing or administering a database server and must reopen
archived projects years later.

## 2. Canonical interview answers

Use these facts as the source of truth. They resolve the material
design, workload, security, transaction, retention, and deployment
questions. Do not invent requirements.

### 2.1 Entities, attributes, and data rules

All generated IDs are signed 64-bit integer surrogate keys generated by
the database. All timestamps are stored in UTC. Text identifiers are
trimmed before storage. Unless stated otherwise, referenced records are
not hard-deleted; status changes preserve history.

-   **Project:** `project_id` PK; `project_code` VARCHAR(32) required
    and unique; `project_name` VARCHAR(120) required; `start_date` DATE
    required. Exactly one Project row exists in each project database. A
    database file represents exactly one project.
-   **Asset:** `asset_id` PK; `project_id` FK required; `asset_tag`
    VARCHAR(64) required; `asset_kind` required and restricted to
    `equipment`, `instrument`, `vehicle`, or `other`; optional
    description VARCHAR(500). Unique `(project_id, asset_tag)`.
-   **Inspection:** `inspection_id` PK; `asset_id` FK required;
    `inspector_name` VARCHAR(100) required; `inspected_at_utc` timestamp
    required; `status` restricted to `draft`, `final`, or `void`;
    `finalized_at_utc` nullable; `void_reason` nullable. A final
    inspection requires `finalized_at_utc`; a void inspection requires a
    nonempty reason.
-   **Measurement:** `measurement_id` PK; `inspection_id` FK required;
    `metric_code` VARCHAR(64) required; `numeric_value` DECIMAL(18,6)
    required and within -1,000,000,000.000000 to +1,000,000,000.000000;
    `unit_code` VARCHAR(16) required and any nonempty project-defined
    unit code is allowed; optional `note` VARCHAR(500);
    `recorded_at_utc` timestamp required. Negative values are allowed
    where physically meaningful. Multiple measurements of the same
    metric in one inspection are allowed; preserve their individual IDs
    and timestamps.
-   **Defect:** `defect_id` PK; `inspection_id` FK required; `severity`
    restricted to `low`, `medium`, `high`, `critical`; `description`
    TEXT required; `status` restricted to `open`, `mitigated`,
    `resolved`, `closed`; `discovered_at_utc` required;
    `resolved_at_utc` nullable. `resolved` or `closed` requires a
    resolution timestamp.
-   **CorrectiveAction:** `action_id` PK; `defect_id` FK required;
    `description` TEXT required; `due_date` DATE required; `status`
    restricted to `open`, `in_progress`, `completed`, `cancelled`;
    `completed_at_utc` nullable. `completed` requires a completion
    timestamp.
-   **Attachment:** `attachment_id` PK; `inspection_id` FK required;
    `relative_path` VARCHAR(512) required; `media_type` VARCHAR(100)
    required; `byte_size` BIGINT required and greater than zero;
    `sha256` CHAR(64) required. Unique `(inspection_id, relative_path)`.
    The file itself is outside the database; absolute paths and paths
    escaping the project folder are prohibited.

### 2.2 Relationships and cardinalities

-   One Project has many Assets; every Asset belongs to the single
    Project row in its file.
-   One Asset has many Inspections; every Inspection belongs to exactly
    one Asset.
-   An Inspection has zero or more Measurements, Defects, and
    Attachments.
-   A Defect has zero or more CorrectiveActions.
-   All foreign keys are mandatory except fields explicitly marked
    nullable.
-   Deleting a parent with dependent history is prohibited. Use status
    changes; do not cascade-delete inspection history.
-   No record in one project file may reference a record in another
    project file.

### 2.3 Data volume and retention

-   Each inspector completes about 20 projects per year.
-   A large project contains about 2,000 Assets, 20,000 Inspections,
    150,000 Measurements, up to 20,000 Defects, and up to 30,000
    CorrectiveActions.
-   One project database must remain below 500 MB excluding external
    photographs and documents.
-   Retain the complete project database for 10 years after project
    close; no row-level purge during that period.
-   Attachments are stored in a project folder beside the database. The
    database stores relative paths, file size, media type, and SHA-256
    hash only.

### 2.4 Workload and reporting

-   One inspector uses one project file at a time. One application
    process is open per file; at most one writer is active.
-   Work is fully offline. There are no web clients, central real-time
    dashboards, synchronization jobs, or remote database connections.
-   Common reads: asset lookup, inspection history, open critical
    defects, overdue corrective actions, and measurement history by
    asset/metric.
-   Common writes: create/finalize/void an inspection, add
    measurements/defects/attachments, and update corrective actions.
-   Normal local searches should complete within two seconds on the
    supported laptop. No separate analytics workload exists.

### 2.5 Transactions and consistency

-   Creating an Inspection and all Measurements and Defects entered in
    that save operation is one atomic transaction.
-   Finalizing an Inspection and recording its final timestamp is
    atomic.
-   A failed save must leave no partial inspection, measurement, or
    defect rows.
-   A finalized inspection is immutable through normal application
    operations. Corrections are recorded as a separate follow-up
    inspection; no silent edits.
-   There is no distributed transaction, multi-writer, or cross-file
    transaction requirement.

### 2.6 Security and privacy

-   The application records the inspector's display name for
    accountability.
-   Authentication and file access are handled by the laptop OS account.
    The database does not store passwords, credentials, or database-user
    accounts.
-   Laptops use full-disk encryption and OS file permissions. Project
    files are not stored on network shares.
-   The office receives a finalized copy and reads it only; it does not
    edit the inspector's live file.
-   No special regulatory certification or database-level row security
    is required.

### 2.7 Business rules

-   Asset tags are unique within the project.
-   Measurement values are required finite decimals; unit codes are
    required but may be project-specific.
-   Severity and status values must match the enumerations above.
-   Completed corrective actions require `completed_at_utc`.
-   Finalized inspections cannot be silently changed or deleted.
-   Attachment paths must remain inside the project folder; files are
    verified against the stored SHA-256 when opened.
-   No financial calculations, geospatial queries, full-text search, or
    external system integration are required.

### 2.8 Deployment and operations

-   Supported OS: Windows 11 and current supported Ubuntu LTS.
-   One self-contained database file per project; no server
    installation, administrator privileges, Docker, or network access.
-   Use the SQLite library bundled with the application runtime; target
    SQLite 3.42 or later.
-   The database file resides on the laptop's local SSD, never on a
    shared network filesystem.
-   Create a consistent backup snapshot after each work shift. RPO is at
    most one shift (12 hours); RTO is one hour.
-   The office copy is transferred as a closed, finalized file package
    containing the database and referenced attachment folder.
-   No replication, multi-site editing, or concurrent editing of copied
    project files is required.

## 3. Exact answers to likely follow-up questions

-   **How many projects per database?** Exactly one. Each project has
    its own database file and exactly one Project row.
-   **Can two inspectors edit the same file?** No. One inspector and one
    application process per file.
-   **Can the office edit the transferred copy?** No. The office reviews
    it read-only.
-   **Are photos stored as BLOBs?** No. Only relative paths and file
    metadata are stored.
-   **Are negative measurements valid?** Yes. The application accepts
    values in the stated numeric range; project procedures determine
    whether a negative value is physically meaningful.
-   **Are there any external integrations?** No.
-   **What happens when an inspection needs correction?** Create a
    follow-up inspection; do not alter a finalized record.
-   **Anything not listed?** It is not required for this scenario. Do
    not infer extra requirements.

## 5. Expected outcome --- evaluator only

**Do not send this section to the agent.**

-   **Expected `selected`:** `SQLite`
-   **Expectation strength:** Strong.

### Why

One portable file per project, offline operation, no server
installation, one active writer, local-only access, and small bounded
data volume directly fit an embedded database. Server DBMSs add
infrastructure explicitly excluded by the deployment contract.

### Design and SQL acceptance checks

-   One Project row per file; project-scoped unique asset tags.
-   Correct FK chain: Project → Asset → Inspection →
    Measurement/Defect/Attachment → CorrectiveAction.
-   Required finite numeric measurements, valid enumerations, and
    completion/finalization timestamp rules.
-   Attachment paths are relative and cannot escape the project folder.
-   Seed must not contain orphan inspections, duplicate asset tags
    within one project, invalid severity/status values, or completed
    actions without completion timestamps.
-   Do not claim SQLite provides multi-writer concurrency or safe live
    editing over a network share.
